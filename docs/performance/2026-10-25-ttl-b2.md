## Method

- `scripts/perf-compare.sh --suite full` on the **final** runtime, one shared
  harness, ten interleaved control/candidate pairs with AB/BA rotation, one
  subprocess per sample, never concurrently. Micro at `-cpu=1,2,4,8`; open-loop
  at the machine-default GOMAXPROCS (8), 4 workers, queue 1024, 3s windows,
  250ms burst window, seed 20261025. Idle and lifecycle ran one pair per side.
- The first ten-pair pass at expiry-burst showed an unstable drop comparison and
  one P99 outlier, so per the plan's "add complete sample pairs when unstable"
  rule the 10K tier was extended to 20 pairs and the 50K tier to 40 pairs, with
  the same harness, machine, and serial interleaving.
- The production reclamation monitor snapshots the whole map every 10ms. Because
  the coarse reading was in the 10–30ms range and disagreed with a finer view,
  both sides were re-measured with one common finer method: a test-only 1ms poll
  of the expiry-heap length (O(1), exact for this fixture, since the 100000
  expiring keys are its only TTL records). This is the plan's "use a common
  measurement method for both sides when near the threshold" rule.
- Go 1.27.0 darwin/arm64, Apple M1 Pro (8 cores). Every load run passed
  `verifyLoadAccounting`; no command exited nonzero.
- `cand/ctrl paired` is the median of the per-pair candidate/control ratios;
  below 1 means the candidate was faster. Percent reduction is `1 − ratio`.

All core scalar operations are within 2.7% and the 0-allocation contracts hold.
A pre-fix sample had measured a ≈5.3–5.6% Lookup regression; the review traced
it to scheduler-notification work on the lookup hit path. The final path
captures and compares the heap root only when it actually removes an expired
target, so a hit or a miss adds no expiry-heap or wake work.

`RenewTTL` — a TTL operation, so outside the "non-TTL" gate — regresses 10% at
cpu=1 and about 50% at cpu=2/4/8 in the synthetic loop that renews the current
earliest deadline on every iteration. That loop changes the heap root every
time, so the §7.1 notify-on-any-change rule makes the worker re-arm. The wake is
not strictly required for a *later* root (the old timer fires and the worker
re-reads), so an earlier-only wake would remove the cost, but it changes the
contract and `Clear`/`Delete` promptness and therefore needs a spec amendment;
it is a design-review input, not a silent code change. Mixed renewal workloads
stay within 5%.

## Reclamation: two common methods

The production monitor counts expired keys by snapshotting the whole map every
10ms; it is the harness's historical metric but has 10ms resolution and heavy
observer cost. The finer method polls the expiry-heap length every 1ms under the
lock (O(1), exact for this fixture). Both methods ran for both sides.

| method | pairs | control ms | B2 ms | paired B2/control |
| --- | ---: | ---: | ---: | ---: |
| production monitor, expiry-burst 10K | 10 | 18.00 | 21.72 | 1.23 |
| production monitor, expiry-burst 50K | 10 / 20 | 9.86 / 10.85 | 24.38 / 26.05 | 2.42 / 2.30 |
| fine 1ms heap-length poll, 50K | 10 | 12.47 | 18.28 | **1.52** (range 1.21–1.73) |
| independent fine replay, explicit 50K | 10 | 25.69 | 29.49 | **1.147** (range 1.082–1.203) |

The coarse monitor's full-map copy competes with the batched cleaner and can
only resolve 10ms steps in a 10–30ms event; it overstates the candidate's ratio.
The plan explicitly requires a common finer re-measurement near this threshold,
so the **1.52× fine result governs the ≤2× gate**, while the coarse 2.30–2.42×
reading stays reported as the harness's default instrument. The finer method is
test-only and was applied identically to both runtimes. The independent replay
also meets the threshold; its manifest explicitly records the rate and other
load parameters missing from the original supplementary manifest. Absolute
durations differ between collections, so each ratio uses its own interleaved
control/candidate pairs.

review found that gap for the gate; the final-runtime A→B2 batch above closes

Attribution: B1 already removed the foreground purge; B2 removes the ticker's
full purge, cutting the valid-tier burst Set P99 by another ~99% relative to B1
and reversing B1's spread-scenario Set regression. In exchange, total
reclamation is 12–16% slower than B1 (batches instead of one purge) and the
self-root-renewal loop pays the values above. The 1K tier is low-signal in both
comparisons.

## Design-review inputs and unresolved items

1. **Reclamation instrument.** The production monitor's 10ms full-map snapshot
   overstates the batched cleaner's reclamation ratio (2.30–2.42× vs 1.52× on a
   common 1ms method). Replacing it with an O(1) expiry-heap-length poll (the
   fine method here) would make the gate instrument-accurate for both runtimes.
   This is a test-harness improvement, not a runtime change; it is not done in
   this round because it would re-baseline historical comparisons.
2. **RenewTTL on a self-root-renewal loop (10% at cpu=1, ~50% at cpu≥2).** Every
   renewal moves the earliest deadline, so the §7.1 rule wakes the worker to
   re-arm. The wake is not strictly required for a later root; an earlier-only
   wake would remove the cost but changes the contract and `Clear`/`Delete`
   promptness, so it needs a spec amendment.
3. **1K rate tier** has only ten burst Set samples and no signal above noop; it
   is reported but excluded from percentage acceptance.
4. **Linux/Windows matrix** was not executed here. The Go 1.18 gate ran on
   darwin/arm64 because that is the only old toolchain present; CI must run the
   real matrix before full acceptance.
5. `GODEBUG=asynctimerchan=1` is unavailable on Go 1.27; the real Go 1.18 run
   is the compatibility evidence.

## Limitations

- One machine/OS/CPU model; the usual benchmark caveats apply.
- Idle and lifecycle scenarios have one sample per side; they are resource
  observations, not percentage verdicts.
- The B1→B2 attribution's load rows predate the lookup fix; the final-runtime
  A→B2 batch is the gate evidence.
- The coarse reclamation monitor remains the harness default, so a future reader
  comparing bundles sees the 2.3× figure; the fine-method bundle and method are
  recorded at `/tmp/reclaim-fine`.
- Raw evidence stays outside the repository; the manifests and checksums are
  the durable record of what ran.
- This report does not rewrite the Stage A baseline or the B1 report.
