## Method

- `scripts/perf-compare.sh --suite full`, one shared harness, ten interleaved
  control/candidate pairs with AB/BA order rotation, one subprocess per sample,
  never concurrently. Micro benchmarks ran at `-cpu=1,2,4,8`; open-loop runs
  used the machine default GOMAXPROCS (8), 4 workers, queue 1024, 3s windows,
  250ms burst window, seed 20261025. Idle and lifecycle ran one pair per side.
- After the final review, the lookup hit path was changed to do no scheduler
  work (`9a34ad6`). The 1K core gate was then re-measured with 20 interleaved
  pairs at every CPU count against the same A control and harness; that batch is
  the gate measurement in this report. The full load scenarios were not re-run:
  the fix only removes work from the live-lookup path (the expired-target
  removal path is byte-for-byte the same work), so the full-batch numbers are a
  conservative upper bound for the candidate.
- Go 1.27.0 darwin/arm64, Apple M1 Pro (8 cores).
- Every load run passed the harness's `verifyLoadAccounting` equations; no run
  reported a nonzero exit.
- `cand/ctrl paired` is the median of the ten (or, for the fix batch, twenty)
  candidate/control ratios; below 1 means the candidate was faster. Percent
  reduction is `1 − ratio`.

| Operation | cpu=1 | cpu=2 | cpu=4 | cpu=8 | Allocs/op |
| --- | ---: | ---: | ---: | ---: | ---: |

| `BenchmarkCache/Set` | 1.014 | 1.013 | 1.005 | 1.014 | 0 |
| `BenchmarkCache/Get` | 0.985 | 0.997 | 0.998 | 0.995 | 1 (contract) |
| `BenchmarkCachePayload/int/Lookup` | 1.003 | 1.003 | 0.999 | 1.006 | 0 |

All core scalar operations are within 2.7%, and the two 0-allocation contracts
hold. An earlier batch measured a ≈5.3–5.6% Lookup regression; the review traced
it to scheduler-notification work on the lookup hit path. The fast path now
captures and compares the heap root only in the branch that actually removes an
expired target (a hit or miss adds no expiry-heap or wake work), and the same
20-pair comparison then measured ≈1.0%. The full-batch load scenarios were
measured on the pre-fix runtime; that lookup path did strictly more work, so
those results are an upper bound and cannot be invalidated by this fix.

`RenewTTL` — a TTL operation, so outside the "non-TTL" gate — regresses 10% at
cpu=1 and about 50% at cpu=2/4/8 in the synthetic loop that renews the current
earliest deadline on every iteration. That loop changes the heap root on every
iteration, and the current §7.1 rule ("notify on any root change") makes each
renewal wake the worker to stop and reset its timer. The wake is not strictly
required for a *later* root: the already-armed timer still fires at the old,
earlier deadline and the worker then re-reads, so no deadline is missed and no
read contract breaks — only promptness changes. The cost is therefore a
consequence of the current contract rather than of correctness. An earlier-only
wake would remove it, but it is a spec amendment that also changes `Clear`/
`Delete` promptness (the current tests require a prompt re-arm there), so it is
left to the design review rather than changed silently. Mixed renewal
workloads, where the root rarely changes, stay within 5%
(`BenchmarkCacheWorkload/RenewTTL-cap1024` 1.040–1.048 in the post-fix batch).

The 100K/1M mixed workloads from the full batch remain noisy on this machine;
their per-file evidence is in the full bundle, and they were not used for a 5%
verdict in the B1 report either. The post-fix batch above covers every 1K core
operation and is the gate measurement.

hold, and the post-review runtime is within 2.7% on every core scalar operation.

control's time. That is a design-review item, not something to fix by silently
changing the batch size or removing samples.

## Design-review inputs and unresolved items

1. **Reclamation wall time (2.17–2.35× at 50K).** 100K due entries become 1,563
   batches of 64, each taking and releasing the cache lock, so the load's
   foreground traffic interleaves with the purge and the complete reclamation
   runs longer even though per-request P99 collapses. The per-batch
   `runtime.Gosched()` is not the cost (1,563 yields are well under a
   millisecond); the cost is the repeated lock handoff and the O(k log n)
   removals spread around the load. A larger batch would shorten reclamation but
   lengthen each foreground stall; yielding only when a writer is waiting needs
   a waiting-writer signal the cache does not currently expose. Both are design
   revisions; the harness monitor also samples only about every 10ms, so a 14ms
   vs 32ms comparison is coarse. The gate remains unmet pending that review.
2. **RenewTTL on a self-root-renewal loop (10% at cpu=1, ~50% at cpu≥2).** Every
   renewal moves the earliest deadline, so the §7.1 notify-on-any-change rule
   makes the worker re-arm. The wake is not strictly required for a later root
   (the old timer fires and the worker re-reads), so an earlier-only wake would
   remove the cost, but it changes the contract and `Clear`/`Delete` promptness
   and therefore needs a spec amendment. Mixed renewal workloads stay within 5%.
3. **1K rate tier** has only ten burst Set samples and no signal above noop; it
   stays reported but excluded from percentage acceptance.
4. **Linux/Windows matrix** was not executed here. The Go 1.18 gate ran on
   darwin/arm64 because that is the only old toolchain present; CI must run the
   real matrix before Stage B acceptance.
5. `GODEBUG=asynctimerchan=1` is unavailable on Go 1.27; the real Go 1.18 run
   is the compatibility evidence.

## Limitations

- One machine/OS and one CPU model; the usual benchmark caveats apply.
- Idle and lifecycle scenarios have one sample per side; they are resource
  observations, not percentage verdicts.
- The reclamation metric depends on the harness's 10ms monitor snapshots near
  the 2× boundary.
- The full-batch manifests may record `git_dirty=yes`: documentation edits were
  uncommitted in the worktree while those runs proceeded. The script exports
  runtime and harness files from the named commits and never reads the
  worktree, so the measured code is commit-pure.
- Raw evidence stays outside the repository; the manifests and checksums are
  the durable record of what ran. The post-review micro gate has its own
  smaller bundle at `/tmp/memcache-b2-fix-micro`.
- This report does not rewrite the Stage A baseline or the B1 report, and it
  does not claim results for platforms or toolchains it did not run.
