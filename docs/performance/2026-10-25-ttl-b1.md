Executed 2026-10-26 (UTC window 2026-10-25T16:15:00Z – 2026-10-25T18:10:11Z) on

## Method

- `scripts/perf-compare.sh --control 12698ab… --candidate 4b6e198… --harness
  1c43221… --comparison-role original --suite full` into a fresh external
  directory (`/tmp/memcache-b1-full-001`, 822 files hashed).
- Go 1.27.0 darwin/arm64, Apple M1 Pro (8 cores), seed 20261025, load workers 4,
  queue 1024, 3s windows, 250ms burst window. `GOMAXPROCS` was unset, so the
  open-loop runs used the machine default (8); micro benchmarks ran at
  `-cpu=1,2,4,8`.
- Ten interleaved control/candidate pairs per repeated measurement, AB/BA order
  rotation, one subprocess per sample, never concurrently. Idle and lifecycle
  scenarios ran one pair per side, matching the Stage A cadence; the manifest
  records that difference.
- Every scenario JSON passed the harness's own `verifyLoadAccounting` equations
  (`attempted == planned`, `completed + dropped == planned`, `unissued == 0`,
  burst and sample equations). A broken run fails the test instead of writing a
  plausible-looking file.
- `paired cand/ctrl` below is the median of the 10 candidate/control ratios for
  that metric; a value below 1 means the candidate was faster. Percent reduction
  is `1 − ratio`.

## Correctness and work bound (must pass before reading performance)

- `make check` (formatting, vet, unit/integration tests, three shuffled race
  rounds) passed on the B1 commit.
- 60s/4-worker model fuzz passed (1,132,618 executions, no corpus written).
- Task 2's physical-snapshot tests pin the bound: a full-cache insert leaves
  exactly `capacity` physical entries (100 items, 99 old) and reclaims one
  entry; spare-capacity writes leave other expired entries untouched; an update
  or a nonpositive-TTL delete touches only its target; a full cache with a due
  heap root keeps every live entry. No test observes intermediate state through
  `Lookup` or `Size`.
- Model/history/invariant suites stay green: the reference model compares live
  state only, so expired physical residue is not mistaken for an error, and the
  structural invariants (map/list/heap, one expiry record per expiring node) are
  unchanged.
- Allocation contract: scalar `BenchmarkCache/Lookup` and `BenchmarkCache/Set`
  report 0 allocs/op at all four CPU counts; `Get` keeps its documented result
  pointer allocation.

## Verdict on B1 alone

| Gate | Result |
| --- | --- |
| Correctness, invariants, race, model, history | **Pass** |
| Foreground reclamation bounded to one extra entry | **Pass** (snapshot tests + first-Set cost) |
| Scalar Lookup-hit and Set-overwrite 0 allocs/op | **Pass** |
| Non-TTL core operation median regression ≤5% | **Pass** for core scalar operations; 1M workload mixes evidence-insufficient |
| Throughput regression ≤5% | **Pass** (generator-limited: completed equals planned in every tier) |
| Drop rate must not rise in any compared tier | **Pass** (candidate dropped 0 everywhere; the control dropped 314 at expiry-burst 50K and 66 at size-burst 50K) |
| Concentrated-expiry Set P99 −50% (burst window) | **Not met**: 10K paired median 0.503 (−49.7%), 50K 0.768 (−23.2%); 1K not eligible |
| Full reclamation ≤2× control | **Not met at expiry-burst 50K**: paired median 2.01× (side medians 10.96ms → 23.92ms, 2.18×). 10K is 1.14× paired (17.49ms → 20.90ms). Triggers the plan's design review |
| Stage B overall | **Not a Stage B pass** |

Interpretation: B1 removes the foreground stall it targeted. The 100K first-Set
cost falls from 7.21ms to 2.19µs, which is why the 10K burst P99 nearly halves.
What remains is the old 100ms ticker cleaner, which still purges every due entry
under the cache lock. At 50K it reclaims in 2.01× the control's time, and on the
spread scenario it concentrates the whole purge into ticker-driven stalls:
ordinary Set P99 rises from 0.162ms to 1.136ms and the mixed burst P99 roughly
doubles at 10K/50K (candidate ≈2.0–2.5ms), even though the Set-only burst P99
improves there. That remaining stall is B2's target (single worker, earliest
deadline, batches of 64), not something B1 can or should claim.

Per the plan, B1 is therefore an intermediate result: its runtime and README
changes stay if B2 passes, and the end-to-end target remains open until B2 is
measured on the same harness.

## Limitations

- One machine/OS and one Go version (1.27.0). Go 1.18 and other platforms were
  not exercised by this measurement batch.
- Idle and lifecycle scenarios have one sample per side; they are resource
  observations, not percentage verdicts. B1 leaves the ticker in place, and the
  idle records confirm it: 30,000 `now()` checks per 1000 empty instances over
  3s, one worker and its 100ms ticker per instance, essentially unchanged from
  the control (30,000 checks, 1000 owned workers, comparable heap in both).
- The 1M-capacity workload mixes are noisy (see above) and get no verdict.
- The B1/B2 attribution split still needs the B2 report; this batch compares A
  against B1 only.
- Raw evidence stays outside the repository at `/tmp/memcache-b1-full-001`; the
  manifest there carries the three full SHAs, per-file runtime and harness
  checksums, environment, every exact command and exit code, and per-file
  SHA256 plus per-run action SHA256. `SHA256SUMS` covers every produced file.
- This report records what was measured; it does not rewrite the Stage A
  baseline.
